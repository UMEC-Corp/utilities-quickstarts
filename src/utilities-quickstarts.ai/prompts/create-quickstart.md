Внешние источники документации (URL) — РАЗРЕШЕНЫ И ОБЯЗАТЕЛЬНЫ:
- `https://api.rumecdev.deviot.cloud/`
- документация нужного микросервиса, найденная через портал
- `https://ws.rumecdev.deviot.cloud/openrpc.json`
- `https://http-identity.rumecdev.deviot.cloud/.well-known/openid-configuration` (стандартная документация Identity/OIDC; оттуда бери `token_endpoint` и связанные параметры)

Эндпоинты:
- Вебсокеты: `https://ws.rumecdev.deviot.cloud/ws`
- Identity: `https://http-identity.rumecdev.deviot.cloud`

Перед генерацией quickstart ты ОБЯЗАН выполнить этап исследования документации.

Обязательный порядок:
1. Определи тип сценария: HTTP, WebSocket/OpenRPC или смешанный.
2. Если есть HTTP-вызовы:
   - открой портал `https://api.rumecdev.deviot.cloud/`;
   - найди карточку/ссылку нужного микросервиса;
   - перейди в документацию именно этого микросервиса (OpenAPI/ReDoc/Swagger);
   - учти, что страница документации конкретного микросервиса может загружаться долго: дождись загрузки контента до **30 секунд** (не делай вывод “документация недоступна” раньше этого таймаута);
   - на странице микросервиса найди и открой **кнопку/ссылку на Swagger** (например, “Swagger”, “OpenAPI”, “API docs”, “Documentation”) и уже по ней получай спецификацию/эндпоинты.
3. Если есть WebSocket/RPC-вызовы:
   - изучи `https://ws.rumecdev.deviot.cloud/openrpc.json`.
4. Если в сценарии для vendor требуется access token для HTTP-вызовов или шаг авторизации через Identity:
   - используй документацию Identity (`.well-known/openid-configuration` + `token_endpoint`), а не документацию бизнес-микросервиса;
   - определяй названия и формат полей запроса только по документации Identity (не придумывай и не переноси поля из текста комментария как готовые имена параметров без подтверждения в контракте);
   - если в комментарии используются доменные названия (`vendorCode`, `vendorSecret`), явно отрази их как бизнес-данные и сопоставь с фактическими полями Identity по документации.
5. Если сценарий смешанный (HTTP + WebSocket/RPC), используй оба источника.
6. Извлеки факты по каждому вызову: endpoint/метод (для HTTP) или RPC method (для OpenRPC), обязательные поля запроса, пример/формат ответа, коды ошибок, требования авторизации.
7. Только после этого формируй сценарии.

Критерии качества (обязательно):
- Каждый шаг с API- или RPC-вызовом в quickstart должен опираться на факты из соответствующей документации.
- Не придумывай endpoint, RPC method, payload, параметры и названия полей.
- Все примеры кода должны быть практически исполнимыми: без псевдокода, заглушек вида `<...>`, "TODO", "примерно так" и без вымышленных полей/методов.
- Если в комментариях/описании есть бизнес-термины, но нет подтвержденных контрактных имен параметров, явно разделяй бизнес-термин и фактическое поле из документации.
- Раздел "Проверенные источники" заполняй полностью и конкретно: URL микросервиса, URL спецификации, список использованных endpoint/RPC method.
- Если по микросервису/OpenRPC не удалось открыть документацию или в ней нет нужных данных — не генерируй вымышленные шаги, а верни ошибку в JSON:
  - status: "need_clarification"
  - reason: "Не найдена/непрочитана/неполна документация нужного источника (microservice/OpenRPC)"


Важно:
- Repo allowlist НЕ ограничивает чтение URL.
- Если URL недоступны из среды выполнения/политик доступа, верни JSON:
  - `status: "need_clarification"`
  - `reason: "Не найдена/непрочитана/неполна документация нужного источника (microservice/OpenRPC)"`
- Весь текст сценария и поле `body_markdown` в ответе — **UTF-8**; кириллица и символы в коде должны отображаться корректно.
